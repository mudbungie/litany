# Design Principles

Quick-reference catalog of the principles shaping this architecture. Canonical source is `docs/ARCHITECTURE.md`; this document is a distillation. It numbers no sections of its own, so a bare `§N` below is always a section of `docs/ARCHITECTURE.md` — the cross-document reference rule in that document's §2.1.

## Disk first
System state — context, messages while in flight, responses, tool calls — lives on disk; processes hold none of it across restart. That includes the model-facing history itself: assistant output and tool results are committed transcript entries (ARCHITECTURE §2.3), never message lists held in executor memory. This is what makes git the substrate at all: history, branching, rollback, replay, and audit collapse to git operations on data that's already there. It is also what eliminates entire classes of bug — lost updates, stale caches, ghost state surviving a crash, in-memory views drifting from on-disk truth — because there is no in-memory truth to drift from. Every other principle below depends on this one.

## Single source of truth
Every piece of data is recorded in at most one place. If git already carries it — branch existence (`git branch --list`), commit history (`git log`), tree contents (`git ls-tree`), the fork point of a branch — we don't also write it into a sidecar state file. If the filesystem already carries it — a file's presence, a directory's contents — we don't also record that in a manifest. Copy is the bug: two sources means a consistency protocol, and a consistency protocol means drift. When in doubt, derive don't mirror. The silent-death health metric (§8), for instance, is enumerated by `git branch --list 'agents/*'`, filtered by the executor-lock liveness probe (§2.11) and step-record framing (§2.9) — the refs and the kernel are authoritative and free.

## Context has one home
Every context-entering artifact is a committed worktree file — delivered messages, assistant step output, tool results — sequenced as the branch's transcript (`messages/NNN-<origin>`, ARCHITECTURE §2.3). Order lives in the filename and assembly is readdir+sort; step records under `steps/` are diagnostic, with zero runtime content reads. The home is necessary, not sufficient: being in the worktree is what makes a file *eligible*, and the role's `manifest.yaml` entry is what actually includes it (ARCHITECTURE §5.1 — the tree bounds, the manifest selects; the transcript tail is the one ungated part). A file in the tree that no role names composes into nothing, which is ordinary and is where token policy lives. Between compactions the assembled prompt only grows at the tail, so provider prompt caches stay warm; compaction is the sole sanctioned reorganization point (ARCHITECTURE §5.5).

## Inspectability first
Every point in an agent's life is a git ref. Replay, counterfactual forks, and debugging are first-class because the state is on disk in an inspectable tree that only grows between compactions — compaction is the sole sanctioned reorganization point (§2.6, §5.5), a bounded rewrite the branch's own executor lands.

## Symmetry of dispatch
User-to-agent, agent-to-child, verifier, and compactor all flow through one primitive: fork a branch off a ref, do work, return a result message (or answer the user, for the root case). No special code paths for user input, reviews, or summarization — everything is an agent. The symmetry extends past spawn: any sender — user or agent — steers a live agent through the same message primitive (§2.11), a deposit into a quiescent agent starts a driver (reprompt is a message, §2.4), and every sender is indistinguishable from a user for the recipient's whole life. The symmetry has a second face, on the recipient's side: a returning child is indistinguishable from a user *to whoever it answers* — both are senders, and a parent waiting on a child is parked exactly as a root agent is parked waiting on the user. Parking is parking; a deposit revives it either way.

## One obvious path
There should be one — and ideally only one — correct way through the system for any given operation. When two procedures look similar, the discipline is to identify the core operation they share and unify them on *that* core, not to open a parallel path and not to broaden the abstraction past where the sharing actually holds. Compaction and verification are dispatches because the core — fork a branch with a goal, do work, return — is identical; stopping the shared path at "dispatch" is deliberate, because the next layer up (what to do with the result — a verifier's lands as a message, a compactor's as a rebase-forward, §2.6) is where they genuinely diverge. Structurally identical operations share code; operations that merely rhyme stay apart. A new procedure earns its place by collapsing onto an existing primitive or by introducing one that is genuinely new, never by sitting in parallel with something it almost is.

## Testability via configuration
Workflow, prompts, and assembly rules are configuration, not code. Experiments become config diffs measured against a task suite, so improvements can be validated without shipping new software.

## Everything through git
A workspace is one repo, agents are branches plus worktrees, configs are commits on descriptively-named branches, steps are commits, returns are messages, and nothing merges — compaction lands by rebase-forward (§2.6). Using git as the substrate gets history, branching, rollback, and replay for free — and fork chooses the *lineage*: an agent's control resolves, at every step boundary, from its governing lineage's current tip (§2.2, bl-403b — configuration is changeable at any time, on any turn), while every commit it ever resolved stays reachable.

## One writer per branch
There is no `main`. A config branch advances only by user config edits; an agent branch advances only by its executor (§2.3). Every commit is provenanced to its lineage's single writer, and even the compaction landing — the one sanctioned rewrite — is a rebase-forward the receiving branch's own executor lands (§2.6).

## Single author per file
The harness assigns write paths per tool call and per child agent so sibling branches never target the same file. This turns "conflict-free work-product transfer" (§2.6) from a convention into a structural guarantee and keeps parallelism safe at scale.

## Read state per step is a real git commit
Step 1 commits the dispatch artifacts (goal.md + soul.md + name) before its model call; step ≥2 reads from the prior step's tip, advanced by the prior step's transcript, side-effect, and delivery commits. Either way, every step's read state is a real git commit, recorded in the step's `meta.json`. Replay re-runs the context assembler against that sha and reproduces the wire input bit-for-bit; the diagnostic `request.json` on disk is not authoritative. Because the transcript is worktree data (ARCHITECTURE §2.3), running assembly and replay assembly are the same read — replay is not a separate mode.

## Tools return synchronously; async rides on the inbox
Provider APIs require paired `tool_use`/`tool_result`, so every tool returns immediately — that clause is load-bearing and survives. What a tool returns is where the redesign bites: a dispatch hands back the child's *address* (its id, §2.11), never its result, and there is nothing to await. The child's result arrives later as a **deposit into the inbox** (§2.5, §2.6) — the one return channel — and a parent that wants it simply goes quiescent and is revived when the deposit lands (§2.11). A parent waiting on a child is parked exactly as a root agent is parked waiting on the user; the handle/`await`/`check` machinery is deleted, because parking-plus-revival already does its whole job. Parallelism is preserved — many dispatches in one step, each child depositing as it ends — without breaking the wire protocol, and content stays on its one channel.

## Return is not a verb
Termination *is* the return. When an agent finishes — or is stopped, or exhausts its budget — the **executor** deposits its result message (§2.6); the model never calls a return tool, because there is no return tool to call. Whose inbox it lands in is the epitaph's decision, one rule with two arms: a **reply** (a final response) answers whoever last prompted this agent — derived from its own transcript, never stored, and for the dispatch step that is the dispatcher, which is why an ordinary child's return reaches its parent — while an **obituary** (stopped, budget-exhausted, died) reports to the dispatcher whoever prompted last, because it states a fact about the tree rather than answering anyone. An operator who prompts an agent's own conversation is answered there and nowhere else. This is the load-bearing automation, not a convenience. A harness that makes the child's result the *return value* of a tool (Claude Code's Agent tool, pi's `subagent()` extension) must instruct the model to close out explicitly, and then pays twice: with **truncation caps** — the result must fit the parent's context, so it is length-limited — and with **stalled parents** when the model simply neglects the close-out tool. litany's result rides its own channel plus a work-product diff (§2.6), so the terminal response can just *be* the terminal response, and no model instruction is needed for it to arrive. The corollary the implementer must hold: the deposit is executor-side, outside the transcript — never a synthesized `message` tool call, which would forge a `tool_use` block the model never emitted and un-terminate the step (§2.3). `message` stays the tool an agent calls when it *chooses* to send.

## Integrations are external binaries
Tools (§3.3) and the provider adapter (§4.4 — brazen's `bz`, one binary for every provider) are separate executables the harness invokes as subprocesses, each with a narrow stdio contract: JSON on stdin/stdout, SIGTERM cancellation, exit codes with defined meaning. The harness owns orchestration, retry, and on-disk state; the binaries own wire protocols, vendor quirks, and credential handling — litany never sees a credential. That keeps the core small enough to reason about, and it is what lets deployments extend the system without patching it: a new tool is a standalone binary, a new provider is a brazen config row, and a bespoke wire dialect is either a brazen contribution or a contract-compatible alternate adapter binary (§4.4 Extensibility).

## Everyone uses the front door
The `litany` CLI is the sole control plane: every procedure-to-procedure invocation — child dispatch, compaction, verification, any workflow-invoked procedure (§6) — goes through it. The harness is a first-class consumer of its own CLI, using the same command surface an external caller would. Disk-as-bus (§3.1) carries state between procedures; the CLI carries commands. Nothing else — no *divergent* library API, no in-process sidechannel, no ad-hoc socket. The command surface has two bindings (§3.4): the exec'd `litany` binary, and a linked library port that is the *same* surface — nothing public in the crate that is not a verb, no verb without its entry — held to parity mechanically in CI, so linking is not a second channel. Three payoffs: every inter-procedure edge is a capturable verb invocation (integration testability); embedding litany in another tool is `exec("litany", ...)` or the exact-pinned linked binding, never a *divergent* API (embeddability); and with only those two channels, back-channel communication has no place to go (operational atomicity as structure, not convention). The front door is the same even when the path up to it is different: the linked binding walks in through the identical verbs, arguments, and semantics the exec'd binary does, and the CI parity check is what keeps every path ending at that one door.

## Frontends are stateless and pluggable
The UI holds no persistent state; every render is a pure function of filesystem state at the current git ref. Its only interfaces to the harness are reading repo paths and invoking the command surface (§3.4, either binding) — no third channel. Two or more frontends (desktop GUI, webclient, TUI) can run against one repo simultaneously because none of them write repo state or share memory; they all observe the same on-disk truth and drive changes through the same command surface the harness itself uses. Pluggability is structural: a new frontend is a new consumer, not a new integration. Direct consequence of "Disk first" + "Everyone uses the front door".

## Regenerability
Any process can die at any time without losing state. Components (harness, tool subprocesses, provider adapters, frontends) restart independently because none hold state across their own termination. The workflow interpreter itself is the currently-executing CLI subprocess (§6) — a baton passed forward by exec, not a daemon — and the operation that drives the chain is `litany advance <workspace> <agent>`. Crash recovery and normal operation are the same operation: `litany advance` takes the lease (adopting the `LITANY_LOCK_FD` fd its predecessor published, or acquiring the §2.11 lock), delivers pending mail, derives from the transcript tail whether a model call is due, runs one step, and exec's the successor `litany advance` — the lock fd riding the exec, so the lease never gaps (§6). There is no distinct "resume"; recovery is just running advance from where the chain happens to be, and no launcher ever decides warrant — the launched driver decides under the lock (§2.11). No process is load-bearing; disk is. The exec reload is not overhead this property tolerates but the mechanism that makes it hold: because exec rebuilds the process image at every hop, no state *can* cross a step boundary, so per-step statelessness is structural, not a discipline maintainers must uphold ("Structure over discipline"; ARCHITECTURE §6). Direct consequence of "Disk first" + "Everyone uses the front door": with no state off-disk and no commands off the CLI, a crashed process leaves nothing orphaned to reconstruct.

## Structure over discipline
When a safety property — statelessness, atomicity, one-writer exclusivity — can be enforced by construction, so the failure it prevents becomes *impossible* rather than merely forbidden, prefer that to a rule maintainers must remember. A property held by structure needs no review to stay true and cannot drift as code changes around it; a property held by discipline survives only as long as every future edit is checked for the leak. The exec baton (ARCHITECTURE §6) is the sharp case: rebuilding the process image at every step boundary makes per-step statelessness structural — nothing in memory *can* cross a step — where an in-process loop would leave it disciplinary, a cached transcript or held-open writer able to accrete and caught only by review. The same move recurs throughout, and is the reason each design reads as "structural, not aspirational": deletion-only compaction bounds the worst case to lost, never corrupted, information (§2.6); disk-as-bus plus CLI-as-control-plane leaves back-channels no place to exist (§3.4); the executor lock is kernel state bound to process lifetime, observed and never stored, so nothing on disk can go stale (§2.11). Reach for a discipline only where structure is genuinely unavailable — and when the delta is a page-cache-warm reload against a model call (§6), it never is.

## Compaction, never compression
Summarizing a branch's work uses a child agent with a constrained toolset (`write_summary`, `mark_for_deletion`). "Deletion-only" is structural — no general filesystem write surface — so the worst case is lost information, never corrupted information. The constraint is on what the compactor may *call*, not on what its request may *name*: it inherits the branch's transcript, so its model call declares the tools that transcript used or the provider refuses a history it was not told about (§2.7, §3.3) — declared is not callable, and the guarantee rides the second. That second fact is not the compactor's own rule but the general one (ARCHITECTURE §3.3, bl-5a1f): every role calls its `tools:` grant plus whatever its procedure injects, and the compactor's grant is empty, so the pair is all it has. Its landing is a rebase-forward (§2.6), surgical because the compactor rewrites only what existed at its checkpoint while the live agent appends past it; the replay is conflict-free by construction, and the exceptions have one answer each — live-branch-wins on a rewritten work product, a loud decline on markers, superseded lands nothing. That last one is also the whole answer to two passes racing to the same summary path: the first landing rebases the second's compaction point away, so the late lander is refused rather than the path being versioned or the write being last-wins. **When** a pass may start is derived the same way, from git and never from a flag: a branch whose dispatched compactor carries no returned mark has already fired its checkpoint and is not due again (§2.7). What may be *nominated* has its own exceptions on the same principle, and they are one rule: what is not the branch's history is not a pass's to shed. The goal is not compaction-eligible in either of the two projections one dispatch writes — `goal.md` and the dispatch entry the same text was deposited as — so a conversation past a compaction still carries the prompt it was started with; nor are the system slot's other two structural wire homes, `soul.md` and `name`; nor is the summary **this pass wrote**, which is the only thing the compacted span leaves behind. Each is declined at the nomination through one predicate, and each is a class rather than a path: an *earlier* pass's summary stays nominable, because superseding it is the compaction (§2.7). Two more members of that class since bl-e8ec (`docs/DESIGN_CONTEXT_ECONOMY.md` §3, §5.3): `facts.md`, a dispatch-written fact, and the **extract** this pass's landing writes. The extract is the one compaction product no model authors — code derives `summary/NNN.refs.md` at the landing from what the compaction removes from context — and it is exactly why the principle is stated on the *toolset*: the model's write surface stays the pair, deletion-only stays structural, and a product that is a pure function of git is correct by construction where prose is correct by judgement.

## Goals are pinned
Each branch's goal sits at the head of context for every model call on that branch, regardless of position in the sequence. This defeats the recency-decay failure mode in deep agent trees, where the last message drowns out the original intent.

## Stops are aggressive but agent-scoped
When a stop fires, that agent's in-flight HTTP is dropped and its own tool subprocesses receive SIGTERM (its limbs, killed by one kernel process-group signal) — better to waste a step than let runaway work continue after a user or parent has pulled the plug. But a stop targets **one agent**: it does not cross into that agent's children, because a parent and child are separate agents, not a process hierarchy. Every executor takes its own process group (root and child alike), so the kernel signal cannot leak across the boundary; an orphaned child finishes and revives its stopped parent by depositing its result (§2.5, §2.11), so stopping a parent strands nothing. Killing a whole subtree is an explicit request — `litany stop --stop-children` walks the id namespace (children of X are exactly the inboxes prefixed `X-`, §2.9) — never a silent side effect of stopping the root.

## Context assembly is deterministic
What the model sees is a pure function of the repo state via `manifest.yaml`. Reproducibility becomes a property of the system, and "why is this in context?" always has a concrete answer.

## Agents manage their own context by `rm`
An agent reduces its context by deleting files — work products and transcript entries alike; the next assembly excludes them. Deletion is the direction that always works: adding a file adds context only if the role's manifest entry names it (§5.1), but removing one removes it from every selection. Context hygiene is an agent-level decision expressed in the native language of the filesystem, not a bespoke API.

## File path as hint
Paths like `summary/003.md` or `skills/git-ops/SKILL.md` ride into context verbatim. Structure in the name is cheaper and usually sufficient compared to bolt-on metadata. (Step records — `steps/<agent-id>/NNN/request.json` etc. — are not context; they live at the workspace root, outside every worktree, and are diagnostic-only — see ARCHITECTURE.md §2.3.)

## Decline illegal operations
Capabilities are code-backed; a config selecting a capability the harness does not implement is rejected at load time. Silent degradation is never preferable to a loud refusal.

## Measure reliability separately from capability
`pass@1` is the primary metric; `pass@5` is tracked alongside it. A workflow that lifts pass@1 without pass@5 is noise reduction; lifting both is a real capability gain — conflating the two hides which is happening.

## Terminology is load-bearing
Contested field terms ("turn", "session", bare "call", "compression") are banned in code, docs, and commit messages. Every term of art has a single definition in `docs/TAXONOMY.md` or the document introducing it, and coinage without approval is not allowed.
