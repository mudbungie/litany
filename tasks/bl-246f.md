Operator report 2026-11-01 (via lernie bl-acc7): the model pick is global — a `/model` from any chat rebinds every chat on the workspace. Model picks should be per-chat.

## Why this is litany's ball first

The role → (provider, model) binding has exactly one home: `providers.yaml` on the followed config commit (ARCH §4.3), read in `prompt::resolve::resolve_worker` (`src/prompt/resolve/mod.rs`). Under follow-the-tip (bl-403b) every chat on a lineage reads the same tip, so a pick is workspace-wide *by construction*; yog cannot scope it without a litany primitive to scope it with.

## Two shapes, and a recommendation

**A. A per-agent model mark — `refs/litany/model/<agent-id>` (recommended).** The exact class the workflow mark already is (`src/workspace/workflow_mark.rs`, ARCH §6): a standing, non-derivable, per-agent override of one control fact, consulted fresh at every hop, winning over the followed tip for *that fact only*, never consumed, reaped with the agent, carried by an archive. Everything else — souls, tools grant, manifest, workflow — keeps following the lineage. The mark carries the role assignment fields (`provider`, `model`, and optionally `effort`, `priority`, since yog writes them into the same assignment). `resolve_worker` overlays it on the assignment it read from the commit; the step record names it beside `config_commit` for provenance. Verb: `litany model <ws> <agent> <provider> <model> [--effort L] [--priority]` and `--clear` back to the lineage's binding; refused before any mark when the role has no row to overlay (same validity-before-mark discipline as retarget). Descent walk-up as the workflow mark does (nearest mark on the chain), so a chat's same-role subagents run on its pick — to be confirmed.

Cost: an ARCH amendment. The workflow mark names a *commit* and its doc says *content lives only in config commits*; this mark would carry content in a blob. The precedent for a blob mark exists (`refs/litany/role/<agent>` carries a role name; `cwd` carries a path), so the amendment is a sentence in §2.2/§6, not a new doctrine — but it must be written before the code.

**B. A lineage per chat, no litany change.** yog does `litany config <ws> <name> --from default` with the new binding, then `litany retarget <ws> <agent> --config <name>`. Works today, but: the chat stops following `config/default` for every *other* control edit (souls, grants, workflow), which inverts bl-403b for exactly the conversations an operator touched; one `config/*` ref per chat accretes; and a chat held at the fork point sees two tips over it and lands in the *held/diverged* state until the retarget consumes. B trades a one-line design amendment for a standing semantic tax on every picked chat. Not recommended.

## Plan (A)

1. ARCH §2.2 / §6 amendment: the model mark beside the workflow mark; DESIGN_CONFIG_FOLLOW.md gains the line that the per-agent override is the one fact that does not follow.
2. `src/workspace/model_mark.rs`: ref, read, write, clear, blob grammar (reuse `PerRepoProviders`'s role-assignment shape for one role).
3. `resolve_worker`: overlay after the assignment read; `WorkerConfig` gains the mark provenance; step `meta.json` records it.
4. `src/cmd/model.rs`: the verb; refusals precede the mark.
5. Tests beside each; e2e: two chats on one workspace, pick on one, the other's next step unchanged; `litany config default` edit still reaches both.

Downstream: yog ball (REMOTE: `model`/`effort`/`priority`/`roles` ops gain an optional `agent` — an edition, not a major; the write drives the new verb when `agent` is present and today's lineage commit when absent; `roles` with `agent` reports the overlaid binding). Then lernie bl-acc7 (selector passes the selected chat; reads back its binding).
