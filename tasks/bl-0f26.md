Round 1, lane comparator.

State of the tree. ARCH §11 rules MCP a deployment-owned concern outside the
core — "No litany code exists or is planned". DESIGN_MCP_BRIDGE.md §1/§5
specifies the answer as an ordinary `litany-tool-<name>` external binary with its
own credentials; §8 enumerates six refusals (no MCP in core, no marketplace, no
second transport, no resident server or daemon, no generic multiplexer tool, no
live catalog queries); §9 records that no bridge has ever been built or
round-tripped, so the design is checked against source rather than against a
working integration.

The comparators, all three, are MCP in BOTH directions:

- codex: `codex mcp add <NAME> (--url <URL> | -- <COMMAND>...)` with
  `--bearer-token-env-var`, `--oauth-client-id`, `codex mcp login <NAME>
  --scopes`; and `codex mcp-server` — "Start Codex as an MCP server (stdio)".
- Claude Code: `claude mcp add --transport http <name> <url> --header …`,
  `--strict-mcp-config`, project-scoped servers gated behind an approval state
  ("shown as ⏸ Pending approval and not connected to"); and `claude mcp serve`.
- hermes-agent: stdio + StreamableHTTP + SSE, one auto-generated toolset per
  server with per-server `tools.include`/`tools.exclude`, a curated install
  catalog; and `hermes mcp serve`, which deliberately exposes web/browser/vision
  /skills but NOT terminal, file tools, delegate or memory — a good model for
  what a served surface should withhold.

The cost is not that a litany agent cannot reach a database — it can, via a
`litany-tool-x` binary, and that is the right shape. The cost is that it cannot
reach the tools somebody else already wrote, and that every one of those tools
must be re-authored here before it exists. That asymmetry compounds: it is the
one gap on this matrix that gets worse every month without anyone touching the
code.

Proposed shape, and it is the one the design already chose. Build what §1/§5
specify: one `litany-tool-mcp-<server>` binary per configured server, carrying
its own credentials, appearing in the tool pool like any other external, and
subject to the same grant gate and tool control. That keeps every §8 refusal
intact — no core code, no marketplace, no second transport, no daemon, no
multiplexer, no live catalog — and closes the gap with an artifact rather than
an architecture change. §9 is explicit that the design has never been
round-tripped, so the first deliverable is one working bridge against one real
server, which is also the only thing that can tell us whether §8`s refusals
survive contact.

Note the related closed ball bl-32c9, which found §9 citing bl-8925 as a filed
follow-up that had been closed unworked — this gap has been noticed before and
lost.

Filed p4: a comparator gap and an ecosystem one, not a defect.
