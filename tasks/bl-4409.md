Round 1, lane comparator (a capability matrix, lernie suite vs codex CLI vs Claude Code vs hermes-agent 0.15.2).

Observation. The shipped tool pool is nine names — `apply_patch, bash, cd,
dispatch, load_skill, message, python, read_file, search_history`
(`template/providers.yaml`, and confirmed in a live world`s `skills/`). None of
them reaches the network. There is no fetch, no search, no browser.

The comparators:

- codex: `--search` — "Enable live web search. When enabled, the native
  Responses `web_search` tool is available to the model (no per-call approval)".
- Claude Code: WebFetch and WebSearch as built-ins; `--restricted` names WebFetch
  explicitly as one of the tools it removes, which is the shape of a harness that
  treats web access as a first-class privilege.
- hermes-agent: eight pluggable search backends (`exa, parallel, ddgs, searxng,
  firecrawl, tavily, brave_free, xai`) plus a 13-tool browser toolset over three
  drivers (Playwright, raw CDP, a stealth Firefox).

Why it is noticed first, not last. The tasks an agent harness is actually asked
to do — read this RFC, what changed in that crate, what does this error mean —
open with a fetch. The workaround is `bash` plus `curl`, which works and is
exactly what the grant gate exists to prevent being invisible: the role`s
`tools:` list says the agent may run a shell, and the fact that it is browsing
the internet is nowhere in the config, nowhere in the descriptors, and nowhere
an operator would look. A `bash` grant is silently a network grant.

Proposed shape, fitting the layer law. This does not need core code and should
not get any. ARCH §4.4`s governing principle is "integrations are external
binaries", and §3.3 already resolves `litany-tool-<name>` from `<data-root>/tools/`
then PATH, with a three-artifact contract (binary, JSON schema, SKILL.md) and a
three-env-var stdio contract. A `litany-tool-fetch` shipped in the same
repository — or merely NAMED in the template so an operator knows what to
install — turns the capability on with a config edit and, more importantly,
makes it VISIBLE: `descriptions/tools/` is re-cut to the role`s grant at every
step boundary (ARCH §3.3), so a role with fetch says so and a role without it
cannot smuggle one through `bash`.

Two things to settle before building, in this order: (1) whether fetch belongs
in the shipped grant of `worker` at all, given that bl-38c2 already found the
shipped grant too narrow in the other direction; and (2) whether the answer is a
fetch tool or the MCP bridge DESIGN_MCP_BRIDGE.md already specifies, since a
bridge would reach every existing fetch/search server rather than one. They are
not exclusive — the bridge is the general path and a fetch tool is the one
integration common enough to be worth shipping — but the general path should be
decided first so the specific one is not a second home for the same fact.

Filed p4: a comparator gap. Nothing is broken; the suite is simply the only one
of the four that cannot read a URL.
