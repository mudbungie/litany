docs/DESIGN_WORKFLOW_SWITCH.md (bl-f928) ships the on-the-fly switch (litany workflow, the workflow mark), and bl-f838's runner compares fork-time variants; no experiment can yet declare 'switch from W1 to W2 at step k or on event E' as a variant under test. Needs an experiment format for the schedule plus a driver-contract extension — the shipped litany-eval-agent would apply the schedule through litany workflow against the run's workspace, the same front door it already uses for litany config. Runner, record, and comparison surfaces stay unchanged: an experiment remains a name resolving to declared content.

---

Premises checked against the tree (2026-09-04), and one that is not in the body.

HOLDS. An experiment is exactly one file: `experiment::resolve` canonicalizes
`experiments/<name>/workflow.yaml` and the runner hands that one path to the driver as
`LITANY_EXPERIMENT`. A schedule is more than one workflow, so the experiment format and the
driver contract must both grow, as the body says.

HOLDS. The driver applies the experiment through the front door — `litany config` with
`$EDITOR` set to `cp -f "$LITANY_EXPERIMENT"` — before it prompts. README ("Run the suite"):
"nothing in the harness reads that variable ... applying the experiment is the driver's job."

MISSING, and it is the actual blocker. The driver's whole agent invocation is one blocking
`litany prompt <ws> <prompt>`, which drives the root's entire first exchange to a terminal
epitaph inside that one process (the §6 prompt-to-advance collapse is still open, ARCH §2.11
note). The driver never regains control between steps, so it cannot "apply the schedule
through `litany workflow` against the run's workspace" at step k the way the body assumes.
There is no interjection point to extend.

Three shapes follow from that, and the choice is a ruling, so this stays open.

(A) A concurrent supervisor in the driver: fork a watcher that polls
`<workspace>/steps/<agent>/` for the step count and runs `litany workflow --config <next>` at
k. REJECT. It races the boundary it aims at — the mark is read at the top of each hop, so a
write landing between one read and the next takes effect at k or k+1 nondeterministically, and
an experiment whose independent variable arrives at a nondeterministic step is not a controlled
one. It also puts concurrency inside a driver whose whole virtue is being a sequence of
front-door verbs.

(B) Declare the schedule inside the workflow — a new §6 action, `switch_workflow(<lineage>)`,
bound to an event. RECOMMENDED SHAPE. It keeps every invariant the body asks for: an experiment
stays a name resolving to declared content, the schedule IS content in `workflow.yaml` rather
than a new axis beside it, and runner, record and comparison surfaces do not move at all.
"Switch on event E" is also strictly the more useful variable than "switch at step k" — a
workflow can express the first and only counts steps by accident. But it adds to §6's CLOSED
action set, which §6 calls the interpreter's vocabulary and explicitly contrasts with what
experiments recombine "without touching the harness". Hence the ruling. Three sub-decisions
come with it:
  - What the target names. The mark names a COMMIT; an action can only name something stable
    across workspaces, so it must name a config LINEAGE and resolve to its head at the moment
    of the switch. The eval driver then lays each workflow in the schedule down as its own
    lineage (`litany config <ws> <name> --from default`, the same `$EDITOR` trick it already
    uses) — a driver extension, but small and through the same door.
  - Who writes the mark. The action writes `refs/litany/workflow/<agent-id>` in-process, which
    makes the harness a writer of a ref the docs currently frame as the operator's act (§6;
    `docs/DESIGN_WORKFLOW_SWITCH.md` §2). Defensible — the mark is already re-read fresh at
    every hop, and a workflow naming its successor is the same class of self-description as
    `dispatch(<role>)` — but it must be stated, and `litany workflow --clear` must stay the
    operator's override.
  - Termination. W1 to W2 to W1 is an unbounded policy loop no budget catches, because a
    switch costs no model call. Cheapest answer with no new state: a switch whose target
    already answers the workflow question is a clean no-op, which is `litany retarget`'s
    existing rule and is derivable from the mark itself.

(C) Drive hop by hop from the driver, writing the mark between hops. Blocked today: no
front-door verb starts an agent without driving it to terminal. It becomes the CHEAPEST shape
the moment the §6 prompt-to-advance collapse lands, because the driver's own loop is then the
step boundary and the schedule needs no new vocabulary at all. That is the strongest argument
against building (A) now.

Recommendation: rule on (B), or park this behind the prompt-to-advance collapse and take (C)
for free. Do not build (A). If (B) is ruled in, the work is one action plus its interpreter
arm, the lineage-resolution and no-op rules above, the driver laying down one lineage per named
workflow, and the experiment growing from one `workflow.yaml` to a directory of them plus the
binding that names them — runner, record and `compare` untouched, exactly as filed.
