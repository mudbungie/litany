Operator ruling (yog bl-223f, 2026-08-30): every component ships a container
image for DEPLOYMENT SANITY, not for internal container semantics. Nothing in
litany uses the container filesystem as a feature; the image is the unit of
install and nothing more.

Deliver, in this repo:

- `Containerfile`, multi-stage. Build under the pinned toolchain
  (`rust-toolchain.toml`, 1.95.0) so the image is reproducible from the same
  pin the gate uses. The runtime layer carries exactly what the binary execs
  and no more.
- `make image`, autodetecting podman or docker, tagging from the crate version.
  It PUSHES NOTHING — the registry is an unanswered question and pushing waits
  on the coordinated publish moment.
- A README section: what mounts where (the XDG roots are the runtime contract,
  and the image carries no harness state), and what the image deliberately does
  not contain.

The runtime layer is decided by what the binary EXECS, which for this engine is
not nothing: `git` (the harness is git-backed and shells to the binary on
PATH), `sh` (the bash built-in tool), and `bz` (the provider adapter, at the
pin `Cargo.toml` holds). `FROM scratch` is therefore wrong here whatever the
linking story, and the reasoning belongs in the file rather than in whoever
remembers it.

`bz` is not optional and the README already says so — every install route needs
it and only `make install` lays it down. An image that shipped the engine
without the adapter would be an install route that cannot answer a prompt.

Proof, not assertion: the built image answers `--version`, and a workspace
verb runs against a mounted empty directory and produces the workspace on the
host side of the mount.
