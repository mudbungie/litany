`make promote-changelog VERSION=0.0.9` landed on main (bl-6726) while bl-d21b was still in the gate. The release PR then merged ON TOP of bl-d21b — origin/main is `299cf13f Merge pull request #19` with `6f0e27c3 [bl-d21b]` as its first parent — so the litany-v0.0.9 tag's own tree carries the brazen `=0.0.14` pin and the re-read of the window survey, while `## [0.0.9]` names neither. The bullet sits under `## [Unreleased]`, where it would be promoted into 0.0.10 and describe a change 0.0.9 already shipped.

That is a milder instance of exactly what bl-6364's sixth guard exists to stop — a version shipping whose own tagged tree does not name what it carries — and it is not a code defect: the guard checks that the heading EXISTS at the gated commit, which is the only thing a machine can check without knowing which deliveries will still land behind the open PR.

The act: move the bl-d21b bullet out of `## [Unreleased]` and into `## [0.0.9]`, at the head of that section. Nothing else moves; `tests/changelog_completeness.rs` measures deliveries since the last `v*` tag and bl-d21b is now before it, so the bullet is not required anywhere — it is required to be true.

The general shape, for whoever promotes next: the promotion is the LAST act before a release, not a scheduled one. Promote when the queue behind the release PR is empty, or expect to correct the section afterwards.

Gates: tests 100 percent, docs, alignment.
