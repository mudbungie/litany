Scenario: lane KNOWLEDGE, round 1. Adopted the learning loop on a notes workspace exactly as docs/DESIGN_LEARNING_LOOP.md §2 describes:

    worker_flush:
      - dispatch(compactor)
      - dispatch(reviewer)
    reviewer_return:
      - stage_proposal
    compaction:
      intermediate: {trigger: every_n_commits, n: 6}

Then asked ONE question: "give me an incident digest; read every file that mentions an incident, one at a time with a separate command per file".

WHAT HAPPENED

    conversation tree branches: 15, depth histogram {0:1, 1:2, 2:6, 3:2, 4:2, 5:2}
    workspace agent branches:   51
    rollup for that one conversation: 4,530,297 tokens

Five levels deep, and every branch below the first level is a reviewer or a compactor. Example ref (elided ids):

    agents/<root>-<reviewerA>-<reviewerB>-<reviewerC>-<reviewerD>

Classified by `soul.md` across the workspace: 7 worker branches, 28 compactor branches, 33 reviewer branches, from nine user questions.

CAUSE

docs/ARCHITECTURE.md excludes a compactor branch from being a compaction subject. A reviewer branch is not excluded. A reviewer forks with the inherited transcript, runs its own steps, crosses its own `every_n_commits` boundary, and its `worker_flush` binding fires — dispatching another compactor AND another reviewer, which each do the same. The recursion has no depth term and no base case; only `budgets.max_depth` would bound it, and yog strips the budgets block at every start by design.

STOP DOES NOT PROMPTLY HOLD IT

    $ yog gesture --agent <root> "/stop children"
    {"exit":0,"kind":"outcome","ok":true}

Thirty seconds later the tree had grown from 35 seats to 37 and spend from 3.4M to 4.1M; it settled only after a SECOND `/stop children`, at 43 seats and 4,527,593 tokens. Plausibly each in-flight step completes and its own return fires another dispatch, so one stop catches only the generation that was already running.

EXPECTED

A reviewer branch is a checkpoint product, exactly as a compactor branch is, and must be excluded from being a compaction subject by the same rule. More generally: no branch a lifecycle binding minted should be able to mint its own.

SEVERITY

p1: it is unbounded spend reached by turning on a documented, seeded feature (`workflows/learning-loop.yaml`) and asking one ordinary question. `n: 6` made it fast; `n: 20` only makes it slower, not finite — the same workspace at n=20 produced 8 branches from 94 commits before the reviewer was even bound.
