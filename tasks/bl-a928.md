Scenario: lane KNOWLEDGE, round 1. A notes workspace whose whole job is long, cited syntheses over a 62-note corpus.

FACT

`src/prompt/dispatch/step_commit.rs:54`:

    pub(super) const DEFAULT_MAX_TOKENS: u32 = 4096;

It is what the committed canonical request carries:

    $ python3 -c "import json;print(json.load(open(\"steps/<agent>/<NNN>/request.json\"))[\"max_tokens\"])"
    4096

There is no `workflow.yaml` key, no `providers.yaml` role key and no manifest key that changes it. The provider row in this workspace's wall carried

    body_defaults = { max_tokens = 32000 }

and it did NOT win: across 1628 model messages in the workspace the maximum `output_tokens` observed was 4096, hit exactly 32 times.

WHY IT MATTERS HERE

Two costs, both measured in this lane.

1. Every synthesis is capped at 4096 output tokens. For a knowledge workspace that is the wrong ceiling — a cited digest over a dozen notes reaches it — and there is no knob to raise it per role or per model.

2. With a reasoning model, the cap is spent on thinking first, so the visible answer or tool call is what gets cut. That is the companion ball: every reviewer `apply_patch` in the learning-loop run arrived as `input: {}` at exactly 4096 output tokens, and the learning loop staged nothing as a result.

The constant's own doc comment says it is "one model call's output ceiling, distinct from the §6 spend budgets and from the §5.2 manifest's `budget_tokens`" — three token limits, and this is the only one an operator cannot state.

EXPECTED

Either a config key (a role-level `max_output_tokens` beside `model`/`tools` in `providers.yaml` is the natural home, since it is a per-role property the way effort is), or the provider row's `body_defaults` winning when it names the key. Today the value is a compile-time constant that no document mentions.

SEVERITY

p2: not a defect in the sense of wrong behaviour, but the one number in the whole stack a knowledge deployment most needs to change, with no way to change it.
