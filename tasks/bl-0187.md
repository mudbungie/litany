The first armed run of the bl-6364 auto-merge job (run 33917762543, gated sha 5907444c) printed `open pull requests: 1` and then `gh: HTTP 504`, and the job went red: under `set -e` a transient GitHub API error on guard 5's head-commit read kills the step before any verdict line is printed.

The job is a reconciler — every wake-up re-judges the whole open set, and wake-ups are plentiful (one per push to main) — so a fact it could not read this time is a HOLD it retries, not a failure. Red is also the wrong signal: it reddens the whole release-plz run, where a red run should mean the tree or the release is broken.

Make each of the three API reads tolerant in the `if ! x="$(...)"` form (safe under `set -e`), printing a hold line naming what could not be read and continuing to the next pull request: guard 5's `commits/<sha>` parent read, guard 6's `contents/Cargo.toml` read and its `contents/CHANGELOG.md` read. Leave the two ACTS loud — `gh pr merge` and `gh workflow run` are not reads, and a failure there is worth a red run. Record the reasoning in the job's header beside the guards.

Gates: docs (the workflow header states the rule), alignment (the reconciler paragraph in the AUTO-MERGE section already promises exactly this behaviour and the code did not deliver it). No Rust changes, so coverage is unmoved.
